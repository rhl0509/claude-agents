# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

This directory is **not** an application codebase — it is a library of **Claude Code subagent definitions**. Each top-level `.md` file is one subagent: YAML frontmatter followed by the system prompt that drives that agent. There is no build, lint, or test tooling here; "developing" means authoring and editing these agent definition files.

The agents are authored in **Korean** and (with one exception) all target the same downstream stack they will be pointed at: **Next.js (frontend) + FastAPI (backend) + MySQL**. That stack lives in *other* repositories — these definitions are the reusable review/analysis tooling applied to it.

**Exceptions**: `ai-workspace-architect.md` is a **meta/workflow agent** (stack-agnostic) that redesigns the *user's own AI working environment* (prompts, custom instructions, CLAUDE.md/SKILL.md, repeat-task rules, per-model strategy). `copy-reviewer.md`, `landing-reviewer.md`, `seo-optimizer.md`, `fact-checker.md`, and `brand-voice-guardian.md` are **content/marketing reviewers** (copy, landing-page conversion, SEO, fact/source verification, brand-voice consistency), and `content-repurposer.md` is a **content generator** that adapts one source into multiple formats. None of them review application code. All still obey the shared read-only + memory conventions below. Finally, `unity-code-reviewer.md` and `game-design-architect.md` are **game-domain agents** targeting **Unity + C# (single-player 2D casual)** — a separate stack from the web one: `unity-code-reviewer` reviews game-engine-specific code defects (MonoBehaviour lifecycle, GC/alloc, frame budget, physics/framerate dependence, fake-null, ScriptableObject patterns), and `game-design-architect` designs game/system structure pre-implementation (core loop, difficulty curve, system decomposition, vertical slice). `game-ui-reviewer.md` reviews the game UI/UX layer (HUD/menu layout, CanvasScaler resolution scaling, safe area, gamepad/touch navigation, readability over moving screens), and `game-feel-reviewer.md` reviews gameplay feel/juice (input leniency like coyote time/jump buffer, hitstop, screen shake, feedback channels). These two carve their boundary by **cause of feedback**: feedback for UI operation → game-ui-reviewer, feedback for gameplay actions (even when shown in the HUD) → game-feel-reviewer. Three more round out the game roadmap: `unity-perf-auditor.md` (runtime perf/rendering — draw calls/batching, overdraw/fill rate, texture compression & memory, physics step, Profiler capture interpretation; it owns the *symptom/measurement* of GC while unity-code-reviewer owns the *code cause*), `playtest-designer.md` (designs human playtest protocols — turning the verification questions from game-design-architect/game-feel-reviewer into participants, tasks, metrics, surveys, telemetry; not automated software tests), and `unity-build-auditor.md` (build/release settings & store submission — Player Settings, build size, scenes, permissions, keystore-commit checks; defers secret storage/CI to devops-reviewer). All seven follow the same read-only + memory conventions. Separately, `memory-recaller.md` is a **meta/infra agent** (stack-agnostic, model `haiku` — the repo's first Haiku agent) that recalls the *user's own file-based long-term memory* (`E:\claude_memory\` date indexes `YYYYMMDD_MEMORY.md` + topic files) and returns only query-relevant facts, so heavy models (Opus/Fable) never read whole indexes. It is read-only (does not write/edit memory — the main session owns storage) and follows the same conventions. Finally, three agents added 2026-07 are stack-adjacent tooling: `refactor-strategist.md` plans **behavior-preserving** refactors (responsibility split/extract, dedup/naming, dependency structure, dead code, change seams — no behavior change), `docs-writer.md` writes **developer docs** (README/architecture overview/onboarding/CONTRIBUTING/ADR) extracted from the code, and `agent-definition-reviewer.md` is a **meta agent** that reviews *this library's own* subagent definitions (frontmatter spec fit, routing-friendly descriptions, least-privilege tools, boundary overlap/gaps, body-norm gaps like injection defense) — distinct from `ai-workspace-architect` (which redesigns the user's cross-model workspace). All read-only, same conventions. Newest (2026-07), `storyteller.md` is a **creative content generator** (stack-agnostic) that fleshes out a user's prompt/skeleton into a finished story (short fiction/narrative/scenario/brand story); it is the repo's **first `fable` (creative-writing model) agent**, and unlike `content-repurposer` (which adapts an *existing* source into other formats) it writes *new* narrative. It generates text only (writes no files) and follows the same read-only + memory conventions. Also new (1.64), `debugger.md` is a **stack-agnostic debugging agent**: every other quality agent either scans code with *no symptom in hand* (code-reviewer, unity-code-reviewer — static review) or *aggregates results* (test-runner), while debugger starts from an **observed symptom** and works backwards (reproduce → observe → falsifiable hypotheses → bisect by code path/time/input/environment → causal chain). Performance is split by **axis, not excluded**: *what is slow* (bottleneck diagnosis) belongs to perf-auditor/db-optimizer/unity-perf-auditor, while *when did it get slow / what change broke it* (regression bisect through git history) stays with debugger — otherwise perf regressions would have no owner. Vulnerabilities route to security-reviewer. Its `Bash` is reproduce/inspect-only (working-tree-mutating `git bisect`/`checkout` are proposed, never run).

## Shared conventions (follow these when adding or editing an agent)

- **Frontmatter schema**: every agent has `name`, `description`, `tools`, `model`, `color`, `memory`, `skills`, `hooks` (plus repo-local `version`, `updated`). Official Claude Code fields: `color` (red/blue/green/yellow/purple/orange/pink/cyan — category grouping in the task list/transcript), `memory: user` (persistent per-user memory in `~/.claude/agent-memory/<name>/`, cross-project; it does **not** write into the reviewed repo), `skills: [agent-conventions]` (preloads the shared operating-norms skill), and `hooks.PreToolUse` (the read-only guard — see below). `version`/`updated` are non-standard but harmless. `name` matches the filename (kebab-case).
- **`model` tiering**: `opus` for deep-reasoning agents (code-reviewer, security-reviewer, db-optimizer, migration-reviewer, data-modeler, design-system-architect, system-architect, ui-ux-reviewer, perf-auditor, devops-reviewer, test-strategy, api-contract-reviewer, dependency-auditor, observability-reviewer, ai-workspace-architect, copy-reviewer, landing-reviewer, seo-optimizer, fact-checker, content-repurposer, brand-voice-guardian, threat-modeler, llm-ai-security-reviewer, unity-code-reviewer, game-design-architect, game-ui-reviewer, game-feel-reviewer, unity-perf-auditor, playtest-designer, unity-build-auditor, refactor-strategist, docs-writer, agent-definition-reviewer, debugger, multiplayer-rule-reviewer, save-data-reviewer), `sonnet` for moderate agents (api-doc-writer, test-runner). `haiku` for purely mechanical work — `memory-recaller` (index/topic-file recall of the user's file-based memory) is the first agent to qualify. `fable` (Anthropic's creative-writing model) for narrative generation — `storyteller` (fleshes a prompt into a finished story) is the first agent to use it. Valid `model` values are `opus`/`sonnet`/`haiku`/`fable`/a full model ID/`inherit`; resolution precedence is `CLAUDE_CODE_SUBAGENT_MODEL` env → per-invocation `model` param → frontmatter → main conversation (the per-invocation param is the escape hatch if frontmatter `model` is ever ignored — cf. anthropics/claude-code#44385).
- **Read-only is enforced, not just promised**: reviewers get a least-privilege `tools` allowlist (`Read, Grep, Glob[, Bash]`) so Write/Edit aren't available for their own work. Because `memory: user` auto-enables Read/Write/Edit for memory upkeep, every agent also runs a `PreToolUse` guard (`hooks/agent-guard.ps1`) that **blocks Write/Edit to any path outside `*-memory`** and blocks clearly state-mutating Bash (SQL DDL/DML, `rm -rf`, git writes). The guard is **fail-open** — only a positive match blocks (exit 2); any parse error, unknown case, or missing script allows the call — so it can never break normal operation, only add a block.
- **Not used, deliberately**: `permissionMode` (its `plan` mode is read-only but would block both memory writes and diagnostic Bash — the `tools` allowlist + guard hook cover read-only better); `disallowedTools` (redundant — the allowlist already excludes Write/Edit for non-memory work). The 2026 spec (docs "Supported frontmatter fields") lists several more optional fields we also skip, each for a reason: `maxTurns` (reviewers are single-pass; no turn cap needed), `mcpServers` (Context7 is already granted directly via `tools`, so no per-agent MCP block), `background` (subagents already default to background as of Claude Code v2.1.198 — we accept the default), `isolation: worktree` (read-only agents never mutate the tree, so no worktree isolation buys anything), and `initialPrompt` (each agent's system prompt already fixes its behavior). `effort` is the one such field we **do** use — see next bullet.
- **`effort: high` — adopted across the `opus` set (1.57)**: the spec's `effort: low|medium|high|xhigh|max` (docs: "Overrides the session effort level. Default: inherits from session") pins a subagent's reasoning depth regardless of what the calling session runs at. Every `opus` (deep-reasoning) agent carries `effort: high` in frontmatter so review/security/design quality doesn't silently drop when invoked from a low-effort session; the `sonnet` (api-doc-writer, test-runner) and `haiku` (memory-recaller) agents are **left to inherit** the session (their work is moderate/mechanical and doesn't warrant a floor). We picked `high` as the baseline, not `xhigh`/`max`: high already lifts depth meaningfully, and the higher tiers cost more time/tokens without measured benefit for static review. **`effort: xhigh` exceptions**: the security cluster — `security-reviewer`, `threat-modeler`, `llm-ai-security-reviewer` (1.58) — because a missed auth bypass / injection / STRIDE-class threat costs far more than the extra reasoning budget; and `ai-workspace-architect` (1.59) — the `/fable` meta-designer runs a skeleton→draft→self-score→rewrite quality loop where deeper reasoning directly raises output quality (its whole reason to exist). Everything else stays at `high`. The one `fable` agent, `storyteller` (added 1.63), likewise carries `effort: high` — narrative quality benefits from the reasoning floor just as the opus set does. Any other agent can be bumped the same way if a class of work proves it needs more. Note this is an **execution-policy** field (like `model`), not a change to any agent's instructions or output contract, so per the 1.42/1.55 precedent it did **not** bump per-agent `version`.
- **Distribution assumption (guard depends on it)**: this set is deployed **user-scoped** via `sync.ps1` into `~/.claude/`, where `hooks` are honored — so the read-only guard stays active. Per the spec, **plugin/marketplace-distributed subagents do not support `hooks`, `mcpServers`, or `permissionMode`**; distributing this set as a plugin would silently drop the guard hook while leaving `memory: user`'s Write/Edit enabled — i.e. the read-only seal weakens to the `tools` allowlist alone. Reconsider the guard strategy before any switch to plugin distribution.
- **`description` is a routing signal**, not a label. Write it so the orchestrator knows *when* to invoke this agent — include concrete trigger situations (e.g. "PR 머지 전", "느린 쿼리 진단") and disambiguate from neighboring agents (security-reviewer's description explicitly defers general review to code-reviewer).
- **Least-privilege tools**: grant only what the job needs. Read-only reviewers get `Read, Grep, Glob`. Add `Bash` only with a documented, narrow purpose: `test-runner` runs tests; `db-optimizer` runs read-only `EXPLAIN`/`SHOW INDEX` *only when the user explicitly asks*; `dependency-auditor` runs read-only `npm audit`/`npm outdated`/`pip-audit` *only when the user explicitly asks*, never install/upgrade; `code-reviewer` uses it solely for `git diff` to scope the review, never to run or mutate code; `debugger` uses it to reproduce (re-run a failing test) and to read history (`git log`/`blame`/`diff`) — never to mutate the working tree, so `git bisect`/`checkout`/`stash` are proposed as steps for the user to run, not executed.
- **Analysis agents do not mutate.** Reviewers state "파일을 수정하지 않는다"; `db-optimizer` proposes DDL but never runs `ALTER`/`DROP`; `test-runner` fixes production code only when explicitly told. Preserve this boundary — it's the core contract of the set.
- **Every prompt ends with an explicit output format** (severity-tagged blocks, tables grouped by resource/tag, a prioritized "Top 3" summary). Keep findings anchored to `파일경로:줄번호`.
- **Uncertainty is surfaced, not guessed**: agents mark unclear items "확인 필요" / "추정" rather than inventing facts. Keep this in new prompts.

## Locations & sync (single source of truth)

- **Source of truth**: the top-level `*.md` files in this directory (`d:\auto_agent`) for agent definitions, `commands/*.md` for slash commands, `launchers/*.bat` for the desktop launcher, `hooks/*.ps1` for the read-only guard, and `skills/<name>/SKILL.md` for preloaded skills. Edit them here only.
- **Runtime location**: Claude Code loads agents from `%USERPROFILE%\.claude\agents\`, slash commands from `%USERPROFILE%\.claude\commands\`, the launcher from `%USERPROFILE%\.claude\launchers\`, the guard hook from `%USERPROFILE%\.claude\hooks\` (agent frontmatter references it as `$env:USERPROFILE\.claude\hooks\agent-guard.ps1`), and preloaded skills from `%USERPROFILE%\.claude\skills\`. After editing, run `sync.ps1` to copy all of them there. Do not hand-edit the runtime copies — they get overwritten on sync.
- **What `sync.ps1` does**: deploys only top-level `*.md` with a frontmatter `name:` (docs auto-skipped), plus `commands/`, `launchers/`, `hooks/*.ps1`, and `skills/`. It *delete-syncs* agents: an agent renamed or removed from this repo is removed from the runtime dir too, manifest-scoped (`.claude\agents\.auto_agent_manifest.txt`) so a user's own personal agents are never touched. Any copy/remove error makes it exit 1.
- **Version/doc workflow**: when you change an agent, follow the sync workflow in `CHANGELOG.md` (작업 규칙) and `README.md` (버전 관리) — bump the agent's frontmatter `version`/`updated`, add a CHANGELOG entry, update the README version summary/table, then run `sync.ps1`.
- Do **not** keep a separate `.claude/agents/` copy inside this repo; it duplicates the global runtime set and drifts. The global set already applies to every project.

## Settings

`.claude/settings.local.json` holds local permission allowances for working in this directory. It is environment-specific, not part of the agent definitions.
