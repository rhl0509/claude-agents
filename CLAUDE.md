# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

This directory is **not** an application codebase — it is a library of **Claude Code subagent definitions**. Each top-level `.md` file is one subagent: YAML frontmatter followed by the system prompt that drives that agent. There is no build or test tooling here; "developing" means authoring and editing these agent definition files. There *is* a linter as of 1.93 — `lint-agents.ps1` checks the definitions against the conventions below and should be run before `sync.ps1` (see the linter bullet in Shared conventions).

The agents are authored in **Korean** and (with one exception) all target the same downstream stack they will be pointed at: **Next.js (frontend) + FastAPI (backend) + MySQL**. That stack lives in *other* repositories — these definitions are the reusable review/analysis tooling applied to it.

**Exceptions**: `ai-workspace-architect.md` is a **meta/workflow agent** (stack-agnostic) that redesigns the *user's own AI working environment* (prompts, custom instructions, CLAUDE.md/SKILL.md, repeat-task rules, per-model strategy). `copy-reviewer.md`, `landing-reviewer.md`, `seo-optimizer.md`, `fact-checker.md`, and `brand-voice-guardian.md` are **content/marketing reviewers** (copy, landing-page conversion, SEO, fact/source verification, brand-voice consistency), and `content-repurposer.md` is a **content generator** that adapts one source into multiple formats. None of them review application code. All still obey the shared read-only + memory conventions below. Finally, `unity-code-reviewer.md` and `game-design-architect.md` are **game-domain agents** targeting **Unity + C# (single-player 2D casual)** — a separate stack from the web one: `unity-code-reviewer` reviews game-engine-specific code defects (MonoBehaviour lifecycle, GC/alloc, frame budget, physics/framerate dependence, fake-null, ScriptableObject patterns), and `game-design-architect` designs game/system structure pre-implementation (core loop, difficulty curve, system decomposition, vertical slice). `game-ui-reviewer.md` reviews the game UI/UX layer (HUD/menu layout, CanvasScaler resolution scaling, safe area, gamepad/touch navigation, readability over moving screens), and `game-feel-reviewer.md` reviews gameplay feel/juice (input leniency like coyote time/jump buffer, hitstop, screen shake, feedback channels). These two carve their boundary by **cause of feedback**: feedback for UI operation → game-ui-reviewer, feedback for gameplay actions (even when shown in the HUD) → game-feel-reviewer. Three more round out the game roadmap: `unity-perf-auditor.md` (runtime perf/rendering — draw calls/batching, overdraw/fill rate, texture compression & memory, physics step, Profiler capture interpretation; it owns the *symptom/measurement* of GC while unity-code-reviewer owns the *code cause*), `playtest-designer.md` (designs human playtest protocols — turning the verification questions from game-design-architect/game-feel-reviewer into participants, tasks, metrics, surveys, telemetry; not automated software tests), and `unity-build-auditor.md` (build/release settings & store submission — Player Settings, build size, scenes, permissions, keystore-commit checks; defers secret storage/CI to devops-reviewer). All seven follow the same read-only + memory conventions. Separately, `memory-recaller.md` is a **meta/infra agent** (stack-agnostic, model `haiku` — the repo's first Haiku agent) that recalls the *user's own file-based long-term memory* (`E:\claude_memory\` date indexes `YYYYMMDD_MEMORY.md` + topic files) and returns only query-relevant facts, so heavy models (Opus/Fable) never read whole indexes. It is read-only (does not write/edit memory — the main session owns storage) and follows the same conventions. Finally, three agents added 2026-07 are stack-adjacent tooling: `refactor-strategist.md` plans **behavior-preserving** refactors (responsibility split/extract, dedup/naming, dependency structure, dead code, change seams — no behavior change), `docs-writer.md` writes **developer docs** (README/architecture overview/onboarding/CONTRIBUTING/ADR) extracted from the code, and `agent-definition-reviewer.md` is a **meta agent** that reviews *this library's own* subagent definitions (frontmatter spec fit, routing-friendly descriptions, least-privilege tools, boundary overlap/gaps, body-norm gaps like injection defense) — distinct from `ai-workspace-architect` (which redesigns the user's cross-model workspace). All read-only, same conventions. Newest (2026-07), `storyteller.md` is a **creative content generator** (stack-agnostic) that fleshes out a user's prompt/skeleton into a finished story (short fiction/narrative/scenario/brand story); it is the repo's **first `fable` (creative-writing model) agent**, and unlike `content-repurposer` (which adapts an *existing* source into other formats) it writes *new* narrative. It generates text only (writes no files) and follows the same read-only + memory conventions. Also new (1.64), `debugger.md` is a **stack-agnostic debugging agent**: every other quality agent either scans code with *no symptom in hand* (code-reviewer, unity-code-reviewer — static review) or *aggregates results* (test-runner), while debugger starts from an **observed symptom** and works backwards (reproduce → observe → falsifiable hypotheses → bisect by code path/time/input/environment → causal chain). Performance is split by **axis, not excluded**: *what is slow* (bottleneck diagnosis) belongs to perf-auditor/db-optimizer/unity-perf-auditor, while *when did it get slow / what change broke it* (regression bisect through git history) stays with debugger — otherwise perf regressions would have no owner. Vulnerabilities route to security-reviewer. Its `Bash` is reproduce/inspect-only (working-tree-mutating `git bisect`/`checkout` are proposed, never run). Newest (2026-07), six **systems-language agents** form a C and .NET cluster, each mirroring the web/Unity review·design·perf trio for a stack the web `code-reviewer` only fallback-covers: `c-code-reviewer.md`, `c-architect.md`, `c-perf-auditor.md` for **C**, and `dotnet-code-reviewer.md`, `dotnet-architect.md`, `dotnet-perf-auditor.md` for **non-Unity C#/.NET** (Unity C# stays with `unity-code-reviewer`). Within each language the reviewer↔perf pair carries the same *code-cause vs symptom/measurement* split as the unity pair. `code-reviewer` now also explicitly covers **Flask (WSGI)** backends alongside FastAPI, and its fallback clause defers C and non-Unity C# to these dedicated reviewers. Two conventions this cluster establishes: (1) **the prefix encodes the runtime, not the language** — `dotnet-` (not `csharp-`) because C# is shared with Unity, so the meaningful axis is Unity-engine (`unity-*`) vs .NET-runtime (`dotnet-*`), not the language name; (2) **promotion gate for future language clusters** (Go/Rust/embedded, etc.): these six are provisioned *ahead of* any project deliberately, so add another language trio only when that language's review/design/perf need recurs across real work — treat further speculative trios as unbuilt until a repo actually uses them. A known adjacent gap this cluster surfaced and 1.74 resolved-by-documenting: `perf-auditor` is **Next.js frontend-only** (pinned explicitly in 1.5), so Python backend runtime perf (FastAPI/Flask) has no dedicated owner — app-level blocking/async misuse routes to `code-reviewer`, DB to `db-optimizer`, and a dedicated backend-profiling agent is deliberately **not** created (deferred until a real backend-perf need recurs, per the promotion gate). The gap is documented, not silently covered. Newest (2026-07-15), `curriculum-designer.md` is a **content/education generator** (stack-agnostic): it does instructional design for human-facing courses/workshops/lessons (backward design — objectives→assessment→activities, Bloom's-verb measurable objectives, prerequisite scaffolding, cognitive-load chunking, slide/handout skeletons), distinct from `content-repurposer` (adapts a *finished* course into other formats) and `docs-writer` (developer docs/tutorials, not human pedagogy). It generates text only and follows the same read-only + memory conventions; neighbor descriptions (`content-repurposer`, `docs-writer`, `ai-workspace-architect`) carry the reverse carve-out so "design a course" never mis-routes. Also new (2026-07-15), four agents extend the systems-language cluster to **Java (JVM)** and **Swift**: `java-code-reviewer.md`/`java-architect.md` and `swift-code-reviewer.md`/`swift-architect.md` — each language gets a **reviewer + architect** pair mirroring the C/.NET trio, but **deliberately without a perf agent** (per the promotion gate above — provisioned reviewer+design only; the reviewers document "no dedicated Java/Swift perf agent yet" as a known gap rather than falsely deferring to one). Reviewers carry `Bash` (git-diff scoping + opt-in read-only static analysis, no build/run); architects carry Context7 (Spring/`jakarta.*`/`@Observable`/NavigationStack are version-sensitive, same rationale as dotnet-architect — c-architect stays Context7-less because C's ABI/standard is stable). The two hub agents carry the reverse carve-out: `code-reviewer`'s fallback clause now defers Java/Swift (not just C/.NET) to these reviewers, and `system-architect` defers Java/Swift structure to these architects. `java-code-reviewer` also notes Android/Kotlin as an adjacent uncovered gap (it reviews server/JVM Java, not the Android framework). Newest (2026-07-15), `project-manager.md` is a **meta/coordination agent** (stack-agnostic, like `ai-workspace-architect`/`memory-recaller`) — the library's first *project-coordination* agent. It turns a multi-task/multi-repo goal into an execution plan (WBS decomposition, dependencies, P0–P2 priority, sequencing/milestones), builds a **routing map** from each task to the right specialist agent in this set, and reports progress from the user's `project_active.md`/memory/`git log`. Crucially the **subagent is not an orchestrator** — subagents cannot invoke other subagents, so it emits a plan/routing/status *as text*. The actual orchestration lives one layer up in the **`pm-orchestrate` workflow** (`workflows/pm-orchestrate.js`, triggered by `/pm-run`): it calls project-manager as the "planning brain", then fans out the routed specialist agents for real via `agentType`, and synthesizes a consolidated report. Because every specialist is read-only, the workflow orchestrates *analysis/design outputs* into one report — the actual code edits remain a follow-up main-session/human step. This is the library's **first workflow**, and `sync.ps1` gained a `workflows/` deploy block (symmetric to commands/hooks/skills) to ship it. Its boundary is "what/in-what-order/by-whom" coordination, carved against the technical designers (`system-architect` = one-feature structure, `game-design-architect` = game systems, `refactor-strategist` = refactor steps), the harness `Plan` builtin (one-task implementation steps), `debugger` (root-cause), `ai-workspace-architect` (the user's AI environment itself), and `memory-recaller` (recall only). `Bash` is read-only git history (`log`/`status`/`diff`) for progress assessment — tree-mutating commands are proposed as steps, never run. Newest (2026-07-16), `cover-letter-tailor.md` is a **content generator (career)** (`opus`, like content-repurposer): it tailors a job-seeker's cover letter (자소서) to a specific job posting — dissecting the JD into required competencies, mapping the applicant's *actual* supplied experience to each (strength graded 강/중/공백), and rewriting per question with 두괄식/STAR/char-count discipline. Its defining constraint, stated as the top-priority norm in its body, is **it never fabricates facts** (no invented career/awards/metrics/credentials — falsification voids a hire and carries legal risk); unmet requirements are surfaced as gaps to fill by asking the applicant, never papered over. Unlike `content-repurposer` (adapts an existing marketing source) and `storyteller` (invents fiction), it works from the applicant's real material into a career document; neighbor carve-outs route marketing copy → copy-reviewer, brand voice → brand-voice-guardian, external fact-check → fact-checker. It generates text only (writes no files) and follows the same read-only + memory conventions. Newest (2026-07-16), `self-reflector.md` is the library's **second `haiku` meta/infra agent** (after `memory-recaller`) and the consumer side of a new **self-improvement loop**: an `observe-capture` UserPromptSubmit hook appends each prompt to `E:\claude_memory\_observations\` (append-only, isolated dir, fail-safe, never touching existing memory), and `self-reflector` distills that cross-session log into atomic, confidence-weighted, evidence-backed learning candidates. It ports ECC continuous-learning's *discipline* (atomic instincts, confidence scoring, evidence-backing) onto the E: single-source memory system **without** its code (which writes outside `~/.claude`, violating the E:-single-source rule) — so the loop stays E:-native. Read-only (proposes candidates; the main session records only on user approval). Boundary: recall-by-query stays with `memory-recaller`, and distilling only the *current* visible session is the `/회고` main-session ritual (no subagent, since the main session sees the whole conversation). The capture hook was originally left in `~/.claude/hooks/` outside this repo's `sync.ps1` pipeline; as of 1.101 it and the other five session/memory hooks are **versioned here** (`hooks/`) and deployed by `sync.ps1` like the guard hook — they were runtime-only with no source copy anywhere, so a lost C: drive would have destroyed the self-improvement loop irrecoverably. Their *wiring* (which hook fires on which event) still lives in `~/.claude/settings.json`, which this repo does not manage. Newest (2026-07-16, 1.87), two **content/marketing** agents fill production gaps that the (mostly reviewer) content set left open — `email-sequence-writer.md` (generator: automated email/lifecycle sequences) and `offer-strategist.md` (strategy designer: the offer itself — value prop/pricing/guarantee/bonus/positioning — upstream of copy the way `game-design-architect` is upstream of code). Both were surfaced by reviewing the community "Marketing Skills" pack (Corey Haines, 60+ skills) against this library and taking only the uncovered gaps (CRO/SEO/copy/social stay with existing owners; measurement/retention/sales deferred per the promotion gate). Same batch added a preloaded reference skill **`design-reference`** (`skills/design-reference/`) injected into `ui-ux-reviewer` and `design-system-architect`: it distills the *methodology* (industry→design mapping, AI-slop cliché blocklist, 5-color palette rules, font pairing, pre-delivery checklist) from the community `ui-ux-pro-max-skill` (MIT © Next Level Builder, attributed) **without copying its 84-style/192-palette/161-rule dataset** — so reviewers can name concrete alternatives instead of only flagging "generic", and the architect can propose an industry-informed starter system when no existing tokens exist. For exhaustive palette/style search the source skill composes alongside (reviewer↔generator complement). Newest (2026-07-18, 1.89), `truth-checker.md` is a **verification agent (stack-agnostic)** — an accuracy-first *answering mode* that decomposes a question/claim into verifiable sub-claims, classifies every piece as confirmed-fact / grounded-inference / unconfirmed-assumption / opinion / can't-verify, refuses to fabricate any fact/number/quote/source (unknown → "확인 불가/추가 확인 필요"), self-reviews before answering, and assigns an **evidence-quality** confidence (0.0–1.0) that triggers a re-examine→rewrite loop below 0.8, ending in a fixed `[명확한 답변]/[신뢰도]/[확인할 점]` format. It is the **second `xhigh` rationale outside the security cluster** (after ai-workspace-architect): the confidence-gated self-revision loop is its whole reason to exist. Boundary: `fact-checker` verifies statements *inside a content draft* pre-publish, while truth-checker verifies an *arbitrary question/claim itself* — both carry the reverse carve-out. Read-only, same conventions; its `WebSearch`/`WebFetch` are verification-only. Newest (2026-07-20, 1.91), `brainstormer.md` is an **ideation generator (stack-agnostic)** that owns the *idea stage upstream of every executor*: where other generators execute a chosen direction (offer-strategist designs the chosen offer, storyteller writes the chosen premise, game-design-architect designs the chosen mechanic), brainstormer produces the *candidates to choose from* — diverge (≥5 distinct lenses: inversion, analogy-transfer, combination, constraint-tightening, extremization, audience-shift, subtraction; 3–5 ideas per lens, near-duplicates culled, judgment deferred) then converge (explicit criteria, default 3 axes: goal-fit / feasibility / differentiation; Top 3 + one high-risk/high-reward wildcard; rejected ideas kept in the full numbered table so the user can overrule). It is `opus`, **not** `fable`, by deliberate decision: its closest neighbors (offer-strategist, game-design-architect, curriculum-designer) are all opus ideation/design generators, half its job (convergence scoring) is analytical, and the fable charter stays narrative-only. Two new *symmetric* pairs (unusual for a generator): brainstormer ↔ offer-strategist and brainstormer ↔ game-design-architect ("diverge before choosing" ↔ "design the chosen direction"), because both neighbors previously claimed ideation-adjacent turf (naming; mechanic seeds). Ideation honesty: ideas are free, but attached market/metric/trend claims are never fabricated (`⚠️검증필요`); user constraints are kept, with promising out-of-constraint ideas flagged rather than silently dropped. Generates text only (writes no files), carries the generator "final text = deliverable, no recap-instead-of-table" contract, same read-only + memory conventions.

## Shared conventions (follow these when adding or editing an agent)

- **Frontmatter schema**: every agent has `name`, `description`, `tools`, `model`, `color`, `memory`, `skills`, `hooks` (plus repo-local `version`, `updated`). Official Claude Code fields: `color` (red/blue/green/yellow/purple/orange/pink/cyan — category grouping in the task list/transcript), `memory: user` (persistent per-user memory in `~/.claude/agent-memory/<name>/`, cross-project; it does **not** write into the reviewed repo), `skills: [agent-conventions]` (preloads the shared operating-norms skill; note `skills/` now holds two kinds — *preloaded* references injected into agents (`agent-conventions`, `design-reference`) and one *user-invocable main-session workflow* (`aws-deploy`), which is a skill rather than a command because it is a long gated procedure, not a one-shot dispatch), and `hooks.PreToolUse` (the read-only guard — see below). `version`/`updated` are non-standard but harmless. `name` matches the filename (kebab-case).
- **`model` tiering**: `opus` for deep-reasoning agents (code-reviewer, security-reviewer, db-optimizer, migration-reviewer, data-modeler, design-system-architect, system-architect, ui-ux-reviewer, perf-auditor, devops-reviewer, test-strategy, api-contract-reviewer, dependency-auditor, observability-reviewer, ai-workspace-architect, copy-reviewer, landing-reviewer, seo-optimizer, fact-checker, content-repurposer, brand-voice-guardian, curriculum-designer, threat-modeler, llm-ai-security-reviewer, unity-code-reviewer, game-design-architect, game-ui-reviewer, game-feel-reviewer, unity-perf-auditor, playtest-designer, unity-build-auditor, refactor-strategist, docs-writer, agent-definition-reviewer, debugger, multiplayer-rule-reviewer, save-data-reviewer, ml-experiment-reviewer, accounting-rule-reviewer, automation-reliability-reviewer, game-localization-reviewer, game-test-strategy, game-audio-reviewer, c-code-reviewer, c-architect, c-perf-auditor, dotnet-code-reviewer, dotnet-architect, dotnet-perf-auditor, java-code-reviewer, java-architect, swift-code-reviewer, swift-architect, project-manager, cover-letter-tailor, email-sequence-writer, offer-strategist, truth-checker, brainstormer, aws-reviewer, ai-code-auditor, codebase-archaeologist, identity-access-architect, video-optimizer, ai-search-optimizer, image-prompt-engineer, proposal-strategist, level-designer, knowledge-gardener), `sonnet` for moderate agents (api-doc-writer, test-runner). `haiku` for purely mechanical work — `memory-recaller` (index/topic-file recall of the user's file-based memory) is the first agent to qualify; `self-reflector` (cross-session distillation of the `_observations` log into learning candidates) is the second. `fable` (Anthropic's creative-writing model) for narrative generation — `storyteller` (fleshes a prompt into a finished story) is the first agent to use it. Valid `model` values are `opus`/`sonnet`/`haiku`/`fable`/a full model ID/`inherit`; resolution precedence is `CLAUDE_CODE_SUBAGENT_MODEL` env → per-invocation `model` param → frontmatter → main conversation (the per-invocation param is the escape hatch if frontmatter `model` is ever ignored — cf. anthropics/claude-code#44385).
- **Read-only is enforced, not just promised**: reviewers get a least-privilege `tools` allowlist (`Read, Grep, Glob[, Bash]`) so Write/Edit aren't available for their own work. Because `memory: user` auto-enables Read/Write/Edit for memory upkeep, every agent also runs a `PreToolUse` guard (`hooks/agent-guard.ps1`) that **blocks Write/Edit to any path outside `*-memory`** and blocks clearly state-mutating Bash (SQL DDL/DML, `rm -rf`, git writes). The guard is **fail-open** — only a positive match blocks (exit 2); any parse error, unknown case, or missing script allows the call — so it can never break normal operation, only add a block.
- **Not used, deliberately**: `permissionMode` (its `plan` mode is read-only but would block both memory writes and diagnostic Bash — the `tools` allowlist + guard hook cover read-only better); `disallowedTools` (redundant — the allowlist already excludes Write/Edit for non-memory work). The 2026 spec (docs "Supported frontmatter fields") lists several more optional fields we also skip, each for a reason: `maxTurns` (reviewers are single-pass; no turn cap needed), `mcpServers` (Context7 is already granted directly via `tools`, so no per-agent MCP block), `background` (subagents already default to background as of Claude Code v2.1.198 — we accept the default), `isolation: worktree` (read-only agents never mutate the tree, so no worktree isolation buys anything), and `initialPrompt` (each agent's system prompt already fixes its behavior). `effort` is the one such field we **do** use — see next bullet.
- **`effort: high` — adopted across the `opus` set (1.57)**: the spec's `effort: low|medium|high|xhigh|max` (docs: "Overrides the session effort level. Default: inherits from session") pins a subagent's reasoning depth regardless of what the calling session runs at. Every `opus` (deep-reasoning) agent carries `effort: high` in frontmatter so review/security/design quality doesn't silently drop when invoked from a low-effort session; the `sonnet` (api-doc-writer, test-runner) and `haiku` (memory-recaller) agents are **left to inherit** the session (their work is moderate/mechanical and doesn't warrant a floor). We picked `high` as the baseline, not `xhigh`/`max`: high already lifts depth meaningfully, and the higher tiers cost more time/tokens without measured benefit for static review. **`effort: xhigh` exceptions**: the security cluster — `security-reviewer`, `threat-modeler`, `llm-ai-security-reviewer` (1.58) — because a missed auth bypass / injection / STRIDE-class threat costs far more than the extra reasoning budget; and `ai-workspace-architect` (1.59) — the `/fable` meta-designer runs a skeleton→draft→self-score→rewrite quality loop where deeper reasoning directly raises output quality (its whole reason to exist); and `ai-code-auditor` / `identity-access-architect` (1.92) — an auth *design* defect is the most expensive thing to reverse after deployment, the same cost profile that put the security trio here; and `truth-checker` (1.89) — its confidence-gated self-revision loop (re-examine & rewrite when confidence <0.8) is the agent's whole reason to exist, the same rationale as ai-workspace-architect. Everything else stays at `high`. The one `fable` agent, `storyteller` (added 1.63), likewise carries `effort: high` — narrative quality benefits from the reasoning floor just as the opus set does. Any other agent can be bumped the same way if a class of work proves it needs more. Note this is an **execution-policy** field (like `model`), not a change to any agent's instructions or output contract, so per the 1.42/1.55 precedent it did **not** bump per-agent `version`.
- **Distribution assumption (guard depends on it)**: this set is deployed **user-scoped** via `sync.ps1` into `~/.claude/`, where `hooks` are honored — so the read-only guard stays active. Per the spec, **plugin/marketplace-distributed subagents do not support `hooks`, `mcpServers`, or `permissionMode`**; distributing this set as a plugin would silently drop the guard hook while leaving `memory: user`'s Write/Edit enabled — i.e. the read-only seal weakens to the `tools` allowlist alone. Reconsider the guard strategy before any switch to plugin distribution.
- **`description` is a routing signal**, not a label. Write it so the orchestrator knows *when* to invoke this agent — include concrete trigger situations (e.g. "PR 머지 전", "느린 쿼리 진단") and disambiguate from neighboring agents (security-reviewer's description explicitly defers general review to code-reviewer).
- **Least-privilege tools**: grant only what the job needs. Read-only reviewers get `Read, Grep, Glob`. Add `Bash` only with a documented, narrow purpose: `test-runner` runs tests; `db-optimizer` runs read-only `EXPLAIN`/`SHOW INDEX` *only when the user explicitly asks*; `dependency-auditor` runs read-only `npm audit`/`npm outdated`/`pip-audit` *only when the user explicitly asks*, never install/upgrade; `code-reviewer` uses it solely for `git diff` to scope the review, never to run or mutate code; `debugger` uses it to reproduce (re-run a failing test) and to read history (`git log`/`blame`/`diff`) — never to mutate the working tree, so `git bisect`/`checkout`/`stash` are proposed as steps for the user to run, not executed.
- **Analysis agents do not mutate.** Reviewers state "파일을 수정하지 않는다"; `db-optimizer` proposes DDL but never runs `ALTER`/`DROP`; `test-runner` fixes production code only when explicitly told. Preserve this boundary — it's the core contract of the set.
- **Every prompt ends with an explicit output format** (severity-tagged blocks, tables grouped by resource/tag, a prioritized "Top 3" summary). Keep findings anchored to `파일경로:줄번호`.
- **Uncertainty is surfaced, not guessed**: agents mark unclear items "확인 필요" / "추정" rather than inventing facts. Keep this in new prompts.

## Locations & sync (single source of truth)

- **Source of truth**: the top-level `*.md` files in this directory (`d:\auto_agent`) for agent definitions, `commands/*.md` for slash commands, `workflows/*.js` for workflows (`pm-orchestrate`), `launchers/*.bat` for the desktop launcher, `hooks/*.ps1` for the read-only guard, `skills/<name>/SKILL.md` for preloaded skills, and `rules/*.md` for path-scoped rules. Edit them here only.
- **Runtime location**: Claude Code loads agents from `%USERPROFILE%\.claude\agents\`, slash commands from `%USERPROFILE%\.claude\commands\`, workflows from `%USERPROFILE%\.claude\workflows\`, the launcher from `%USERPROFILE%\.claude\launchers\`, hooks (the guard + the six session/memory hooks) from `%USERPROFILE%\.claude\hooks\` (agent frontmatter references it as `$env:USERPROFILE\.claude\hooks\agent-guard.ps1`), preloaded skills from `%USERPROFILE%\.claude\skills\`, and path-scoped rules from `%USERPROFILE%\.claude\rules\`. After editing, run `sync.ps1` to copy all of them there. Do not hand-edit the runtime copies — they get overwritten on sync.
- **What `sync.ps1` does**: deploys only top-level `*.md` with a frontmatter `name:` (docs auto-skipped), plus `commands/`, `workflows/`, `launchers/`, `hooks/*.ps1`, `skills/`, and `rules/` (7 deploy targets total). It *delete-syncs* agents: an agent renamed or removed from this repo is removed from the runtime dir too, manifest-scoped (`.claude\agents\.auto_agent_manifest.txt`) so a user's own personal agents are never touched. Any copy/remove error makes it exit 1.
- **Single registry (`registry.json` + `build-registry.ps1`, 1.94)**: the full agent roster used to be hand-maintained in four places (README table, AGENTS table, the CLAUDE table above, and `project-manager.md`'s routing reference). Hand-maintained rosters rot — PM's was missing 16 of 73 agents (22%) when measured, so the coordinator could not route work to anything added since 2026-07-15. `registry.json` now holds the one curated copy and deliberately stores **only what cannot be derived**: `group` and `note`. Everything else (tools/model/effort/version/description) stays in each agent's frontmatter as the source of truth. `build-registry.ps1` regenerates PM's routing block between `<!-- ROUTING:BEGIN/END -->` markers; `-Check` reports drift without writing (exit 1) and the linter delegates to it. Generation is deliberately narrow — README/AGENTS tables carry hand-written nuance, so the linter only verifies a row exists per agent rather than regenerating them. When adding or removing an agent: edit `registry.json` → run `build-registry.ps1` → run `lint-agents.ps1` → `sync.ps1`.
- **Definition linter (`lint-agents.ps1`, 1.93)**: run it before `sync.ps1`. ERRORs (frontmatter fields, `name`↔filename, mutating tools in the allowlist, missing `agent-conventions` skill or guard hook, non-Korean description, **missing boundary-delegation clause**, **broken delegation link**) block; WARNs need judgement. Three checks are ours and not in the upstream script it was ported from: boundary-clause presence, broken links, and **routing orphans** — an agent nothing else delegates to will never be picked by the router, which is the failure mode reverse carve-outs exist to prevent. Role suffixes are derived from the existing agent names rather than hardcoded; `$RoutingEntryPoints` documents the one intentional orphan (`project-manager`, the coordination layer above everything). The script must stay UTF-8 **with BOM** and CRLF or PowerShell 5.1 reads it as ANSI and the Korean turns to mojibake.
- **Version/doc workflow**: when you change an agent, follow the sync workflow in `CHANGELOG.md` (작업 규칙) and `README.md` (버전 관리) — bump the agent's frontmatter `version`/`updated`, add a CHANGELOG entry, update the README version summary/table, then run `sync.ps1`.
- Do **not** keep a separate `.claude/agents/` copy inside this repo; it duplicates the global runtime set and drifts. The global set already applies to every project.

## Adjacent folders (the three-folder split, 1.101)

Three sibling folders on `D:` look related and are routinely audited together. Only one of the three seams is a real dependency — the other two are deliberate non-relationships, written down here so "no link" reads as a decision rather than an oversight.

| Folder | What it is | Relationship to this repo |
|---|---|---|
| `D:\auto_agent` | this library (agent definitions → `~/.claude`) | — |
| `D:\auto_agent_content` | the user's **brand-voice canon** (`voice.md`), not a git repo, not code | **Real dependency.** `brand-voice-guardian` (and the `/voice` command) name `D:\auto_agent_content\voice.md` as source #2 and read it directly when the working project has no local `voice.md`. Read-only: the library never edits the canon. Before 1.101 the path was recorded *only inside `voice.md` itself*, so `/voice` fell through to "no baseline" everywhere and its fallback told the user to create a *second* voice.md — a drift generator. |
| `D:\auto_agent_secagent` | standalone Python security tool (`anthropic` SDK, SAST/BUGS/DAST/CI) | **Deliberately unlinked.** Different contract: a separate process with its own API key and CI exit codes, not a subagent. It is never routed to by an agent description, and no agent defers to it. The split of use is written in that repo's `CLAUDE.md`: subagents for in-session review of code being edited, secagent for CI gating, SARIF upload, live-app DAST, and the standalone exe. It also holds **intentionally vulnerable fixtures** (`examples/vulnerable_*`) plus a real `.env`, which is why it carries a `CLAUDE.md` telling reviewers to exclude them — pointing `/sec` at that folder without it produces a false-positive flood. |

Do not "unify" these three. The content folder is user data with a different lifecycle (it changes when the user's writing samples arrive, not when agents change), and secagent's value is that it runs *outside* a Claude Code session.

## Settings

`.claude/settings.local.json` holds local permission allowances for working in this directory. It is environment-specific, not part of the agent definitions.

`~/.claude/settings.json` (hook wiring, permission denies, model/effort) is **not** managed by this repo — only the hook *scripts* are versioned here. Changing which event fires which hook is a manual edit there.
